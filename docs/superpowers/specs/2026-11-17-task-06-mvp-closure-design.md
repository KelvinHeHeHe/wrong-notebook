# 任务 06：MVP 收口设计

> 状态：待确认（验收口径已选择分段证据矩阵）
> 日期：2026-11-17
> 前置：任务 02～05 已合入 `main`，GitHub CI（含 E2E）已通过。

## 1. 意图

本任务把家庭小学生 AI 智能错题系统从“各功能分别完成”收口为“有一套可重复执行、可审阅、可发布的 MVP 证据”。目标用户仍是单个家庭账号，核心路径是：导入外部整卷、人工校对、打印纸质试卷、拍照回传、人工复核、确认成绩、查看趋势、备份并恢复。

本任务不新增产品能力。优先复用现有迁移、备份、Playwright 和 CI 设施，只在验收证据有真实缺口时补测试或测试辅助代码。

## 2. 当前事实

- `BACKUP_VERSION` 已是 13；v11、v12 兼容导入已有单元和真实 SQLite 集成测试。
- `database-migrations.test.ts` 已验证全新数据库完整迁移、重复部署幂等以及关键旧行升级保留。
- `exam-import.spec.ts` 已验证两页照片导入、单页失败重试、校对发布和打印。
- `exam-attempt.spec.ts` 已验证打印卷回传、逐题复核、确认幂等、趋势、v13 导出和空账号恢复。
- GitHub CI 已验证公开历史、lint、单元测试、集成测试、覆盖率、生产构建、Windows 签名校验、双架构 Docker 构建和 E2E。
- 任务 01 的 `docs/PROJECT_AUDIT.md`、`docs/MVP_PLAN.md`、`docs/DATA_MODEL.md` 仍是主工作区未跟踪设计稿，其中“尚未实现”“v12”“3512/88 测试”等信息已过时。
- 当前工作区没有 `../wrong-notebook-github-pages`，本任务不能安全修改或发布官网。

## 3. 目标

1. 给全新 SQLite 和既有 SQLite 升级各提供一条隔离、自动化、不会触碰 `prisma/dev.db` 的验收路径。
2. 固定 v11 → 当前 v13、v12 → 当前 v13、v13 往返的兼容行为，确认图片、作答、评分、趋势所需关联不丢失。
3. 用可追踪矩阵证明完整家庭流程的每一段都由现有或新增自动化测试覆盖。
4. 把任务 01 的三份文档从设计态更新为实施后事实，并加入仓库。
5. 生成一份面向维护者的 MVP 验收报告，记录命令、环境、结果、已知限制和发布前待办。
6. 让完整 CI、全量 Playwright、Python publication 测试和公开历史检查在最终分支上通过。

## 4. 非目标与反目标

- 不创建版本标签、GitHub Release、npm 包、镜像或安装包发布。
- 不新增 Python OCR、消息队列、对象存储、云数据库或第二套试卷模型。
- 不重写现有业务流程，不为了形成“单一巨型用例”复制导入和回传测试代码。
- 不操作本地真实 `prisma/dev.db`，不删除或迁移用户数据。
- 不把 `config/setup-token` 或任何凭据、密钥、真实家庭数据纳入提交。
- 不因官网仓库缺失而虚构文件或修改上游 `margrop` 仓库。

## 5. 方案比较

### 方案 A：只复跑现有 CI 并更新文档

成本最低，但无法明确回答“旧数据库升级断点在哪里”“v11 导入后能否再导出为 v13”“完整流程的每个阶段由哪个测试负责”。不采用。

### 方案 B：增加单一超长 MVP Playwright

把导入、打印、回传、趋势和恢复全部放进一个浏览器用例，表面上最直观，但会重复现有两条昂贵用例、增加测试时长和失败定位成本。一个非关键 UI 变化会让整条验收失去信号。不采用。

### 方案 C：证据矩阵 + 最小缺口测试（用户选择）

保留现有分段 E2E，以数据主键、状态和备份不变量串联验收语义；只新增必要的接缝断言和跨版本再导出断言。最终用验收矩阵列出每个用户步骤、自动化证据、命令和结果。该方案最大化复用，失败时能定位到迁移、备份、导入、回传或趋势中的具体层次。用户明确接受它不是“同一张试卷贯穿所有浏览器步骤”的单一巨型用例。

## 6. 验收架构

### 6.1 数据库矩阵

全新数据库：继续通过 `database-migrations.test.ts` 在临时目录运行全部正式迁移，校验 Prisma 模型、外键、索引与重复部署幂等。

既有数据库：锁定断点为 `20261105135634_add_telemetry_tables` 已应用、`20261108090000_add_exam_attempts` 尚未应用。现有“很老数据库升级到当前”的用例已经覆盖旧数据、默认字段和约束，不重复新增同义用例；只在现有测试无法明确证明该近端断点时扩展它。测试先部署到断点，插入既有用户、学科、错题、旧试卷、题目和练习记录，再部署剩余迁移，断言：

- 原记录数量和关键字段不变；
- 旧试卷默认为 `origin='generated'`；
- 新页面、作答和评分表存在且为空；
- 新外键和唯一索引有效；
- 第二次 `migrate deploy` 不再改变数据库。

测试只使用 `mkdtemp` 下的 SQLite，不读取或覆盖开发数据库。

### 6.2 备份兼容矩阵

在现有真实 SQLite 备份集成测试上补最小断言，不复制已经覆盖的双作答、重复导入和隔离场景：

- v11 文件导入后，再通过当前导出接口导出，版本为 13，旧试卷数据保留，新集合为空；
- v12 文件导入后，缺失的 `ExamAttemptPage.recognitionResult` 规范化为 `null`，再次导出的版本为 13；
- v13 外部试卷、页图、两次独立作答、逐题评分、候选识别结果和 `PracticeRecord` 关联完整往返；
- 重复导入保持幂等，跨用户或跨试卷关联不被恢复。

不升级备份版本，因为任务 06 不新增持久化字段。

### 6.3 家庭流程证据矩阵

不新增巨型 E2E，而是在 `docs/MVP_ACCEPTANCE.md` 中把每一步映射到稳定证据：

| 用户步骤 | 自动化证据 |
| --- | --- |
| 导入照片、部分失败、单页重试 | `e2e/exam-import.spec.ts` |
| PDF 全页渲染、页数限制与异常文件 | `src/__tests__/unit/exam-import-client.test.ts` 及现有 PDF E2E/单元测试 |
| 校对、发布、进入现有详情与打印 | `e2e/exam-import.spec.ts` |
| 导入发布后的真实试卷进入纸质回传入口 | 在 `e2e/exam-import.spec.ts` 增加从详情页打开 `/exams/:id/attempts/new` 的桥接断言 |
| 打印卷拍照回传、两阶段识别 | `e2e/exam-attempt.spec.ts` |
| 人工映射、复核、部分分、确认幂等 | `e2e/exam-attempt.spec.ts` |
| 错题/练习记录/掌握度入账 | `e2e/exam-attempt.spec.ts` 与确认集成测试 |
| 成绩趋势与详情跳转 | `e2e/exam-attempt.spec.ts` 与统计集成测试 |
| v13 导出、空账号恢复、同日双作答保留 | `e2e/exam-attempt.spec.ts` 与备份集成测试 |
| 全新库与既有库升级 | `database-migrations.test.ts` |
| AI 外发前用户同意与 Provider 配置 | `e2e/auth-flow.spec.ts`、`src/__tests__/integration/ai-consent.test.ts`、作答识别 SQLite 集成测试及 E2E 本地模型配置 |

报告同时说明：分段测试共享的是相同生产模型和 API 不变量，而不是测试间的临时数据库；这让每段可以独立失败和重跑。

### 6.4 文档收口

把三份任务 01 文档纳入版本控制并更新为实施后事实。源文件只从主工作区读取 `docs/PROJECT_AUDIT.md`、`docs/MVP_PLAN.md`、`docs/DATA_MODEL.md`，在任务分支中重建并校准；不得复制同目录外的 `config/setup-token` 或其他未跟踪文件：

- `docs/PROJECT_AUDIT.md`：保留原始审计结论，增加任务 02～05 实施状态、当前测试数和风险变化。
- `docs/MVP_PLAN.md`：把任务 02～05标为已完成；把备份 v12 计划改为实际 v13；任务 06 状态改为本次验收结果。
- `docs/DATA_MODEL.md`：从“建议/尚未修改”改为“已实现模型”，以当前 Prisma Schema 和迁移为准，保留容量与后续演进建议。
- 新增 `docs/MVP_ACCEPTANCE.md`：记录验收矩阵、最终提交 SHA、验收日期、Node/macOS、执行命令、当次测试数量、结果、环境差异、已知限制与发布前清单；测试数量是当次证据，不作为永久契约。
- README 和 Wiki 只修正与事实不一致的版本号或链接，不重复大段验收内容。

英文用户文档只在用户可见行为或说明变化时同步；本任务主要是维护者证据，不新建三份审计文档的英文副本。

### 6.5 发布准备边界

最终分支达到“可发布”但不执行发布。发布摘要直接作为 `docs/MVP_ACCEPTANCE.md` 的章节，不更新 `CHANGELOG.md`：

- 工作区干净；
- 公开历史检查通过；
- 无 `npmmirror` 锁文件地址；
- 未跟踪凭据未进入提交；
- 本地 `scripts/ci.sh` 与全量 E2E 全绿；GitHub Actions 只在用户选择推送后作为补充证据，不是本地分支完成的前置授权；
- 发布说明列出功能、迁移兼容、备份版本和已知限制；
- 官网同步因仓库缺失列为发布前外部待办。

## 7. 失败处理

- 如果新增验收揭示业务缺陷，先写最小回归测试，再单独修复和提交；不把修复藏在文档提交中。
- 如果失败来自本机 Prisma Schema Engine，允许按已记录基线使用 `RUST_LOG=info`，但不把该变量固化为产品要求。
- 如果全量 E2E 出现现有不稳定性，保留报告和重跑证据，只有确认代码缺陷时才修改业务。
- 官网、生产签名、发布凭据或家庭真实样本缺失时，记录为外部待办，不伪造成功。

## 8. 验收标准

1. 全新 SQLite 和考试 MVP 前 SQLite 都能在临时目录完整部署到当前 Schema；旧数据无损，新表/索引/外键正确。
2. v11、v12 导入后可按当前格式 v13 再导出；v13 完整往返和幂等测试通过。
3. `docs/MVP_ACCEPTANCE.md` 能逐项定位完整家庭流程的自动化证据及结果。
4. 三份任务 01 文档与当前实现一致，不再把已实现功能写为未来设计。
5. `npm run lint`、TypeScript 检查、全量 Vitest、全量 Playwright、Python publication 测试、生产构建和公开历史检查全部通过。
6. 不修改业务 Schema，不升级备份版本，不触碰真实数据库，不创建发布标签。

## 9. 已知发布前待办

- 官网仓库不在当前工作区，需要在真正发布前同步中英文功能说明。
- 家庭真实样本的识别/评分 95% 目标需要用户提供脱敏样本；当前自动化使用合成夹具，只证明流程与安全边界。
- Windows 生产签名仍依赖 SignPath 生产证书与人工批准；本任务只验证签名检查逻辑。
- 本地图片继续存 SQLite/JSON 备份；容量超过家庭可接受范围后再评估文件存储适配器。
